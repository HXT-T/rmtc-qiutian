# 新手讲解：算法思路、代码结构、部署与启动

写给第一次接触这个项目的人。只讲参赛程序本身（`training_lab/contestant`），不涉及练习裁判、模拟器和批量测试。
更细的模块说明见 [代码详解](代码详解.md)，检录录屏步骤见 [检录清单](检录清单.md)。

## 一、先弄清楚程序在干什么

比赛里每支队伍控制一台机器人。裁判每隔一个 **Tick**（第一阶段 100 ms、第二阶段 500 ms）做三件事：

1. 把"我这台机器人现在看到什么"发给我们（**感知**：自己的位置和血量、周围 9×9 格子里的资源、障碍、敌人、分数）；
2. 等我们回一个**动作**：移动（上下左右）、攻击（某个方向）、防御、或者等待；
3. 结算所有队伍的动作，进入下一个 Tick。

第二阶段还会不定时广播**公告**（文字形式的随机事件，比如"某区域即将爆炸""某时段移动方向会颠倒"），
规则要求必须交给主办方统一的大模型去理解，程序本身不许用关键词去解析文字。

第二阶段的分数大致是：

```
分数 = 0.25 × 收集的资源（最多算 120） + 5 × 完成的任务数 + 15 × 有效伤害（最多算 500）÷ 500
```

有效伤害 = 打出的伤害 + 击杀奖励 − 每死一次扣 60。所以程序的目标就是：**多捡资源、做任务、打伤害，同时少死。**

所以整个程序就是一个循环：**收到感知 → 想清楚 → 回一个动作**，每个 Tick 一次，一场 500 次。

## 二、每个 Tick 程序怎么"想"

可以把它想成一个人在玩游戏，每一步都按下面的顺序思考：

### 1. 看清楚：检查感知是否合法（`protocol.py`）

裁判发来的是一段 JSON 文本。程序先逐项检查：坐标在不在地图里、血量是不是数字、Tick 是不是比上次新……
不合法就丢掉，不会让一份坏数据带偏决策。如果同一个 Tick 被重发了，就直接把上次的动作再回一遍，不重复计算。

### 2. 记下来：维护一张"自己画的地图"（`planner.py` 里的 WorldMemory）

视野只有 9×9，地图却有 24×24。程序把每次看到的东西记下来：哪里有墙、哪里有资源（以及最后一次看到它是什么时候）、
敌人最近出现在哪、哪些格子还没去看过。走到看得见的地方发现资源没了，就从记忆里删掉。

### 3. 听公告：让大模型把文字翻译成"规则"（`ai.py`、`events.py`）

一有新公告，程序在**后台线程**把公告发给统一 AI 网关，**不阻塞当前 Tick**（大模型可能要几秒才回）。
模型回来的是结构化的事件列表（什么事件、哪些格子、从第几 Tick 到第几 Tick），程序会逐条检查格式和范围，
合格的才放进"事件簿"。之后寻路时就会知道"这块地第 200–220 Tick 会爆炸，别站那儿"。

模型调用失败也没关系：程序照常决策，只是暂时不知道这条事件，过一会儿会重试。

### 4. 定目标：现在最值得去哪（`planner.py` 里的 route）

先处理紧急情况：如果马上要爆炸的区域罩住了自己，先撤离。否则列出所有候选目标并估算"值多少分"：

- 已知资源：价值 × 是否还新鲜 × 能不能比敌人先到；
- 任务点、回血点等事件机会；
- **没探索过的区域**：开局时去看看可能藏着资源（按地图大小估算期望价值，越到后期越不值钱）。

然后用**束搜索**（beam search）排一个"先去 A 再去 B 再去 C"的顺序：每一步只保留最好的 20 条路线、往前看 4 个目标，
按"总收益 ÷ 总路程"挑最划算的一条。路程用 Dijkstra 最短路算，会绕开墙和危险区域。
第一阶段地图小、没有敌人，资源能全部走一遍时直接算最短巡回路线（最近邻 + 2-opt 优化）。

最后只取这条路线的**第一步方向**交给下一步。

### 5. 做决定：这一 Tick 具体做什么（`engine.py` 里的 `_choose`）

把所有可选动作都打一个分，选最高的：

| 动作 | 加分 | 扣分 |
|---|---|---|
| 攻击 | 预计打出的伤害（对手可能在防御，会打折）、可能的击杀奖励 | 对手反击的风险 |
| 防御 | 减少受到的伤害 | 这一步没有前进 |
| 移动 | 朝目标前进、顺路捡资源 | 走进敌人射程或危险区的风险 |
| 等待 | — | 原地挨打的风险 |

"风险"的算法：估计这一 Tick 会被打掉多少血，乘一个"怕死程度"系数；如果可能直接被打死，再额外扣掉"死一次少 60 有效伤害"对应的分数。
"怕死程度"由**决策类型**决定，现场唯一允许切换的就是它：

| `decision_type` | 风格 |
|---|---|
| `balanced`（默认） | 收集与战斗平衡 |
| `collect` | 更重视捡资源、更怕挨打 |
| `combat` | 更愿意打架 |
| `survive` | 最保守，尽量不死 |

### 6. 回动作，写日志（`ros_node.py`、`audit.py`）

动作带上本帧的 Tick 和场次编号发回裁判。同时把"做了什么、为什么、算了几毫秒"写进 JSONL 日志，赛后可以用 `analyze` 汇总检查。

## 三、两个阶段的区别

同一份代码，启动时用 `--stage` 选择：

- **第一阶段**（`--stage 1 --team A`）：单人收集，没有敌人和公告，不需要 AI 网关和令牌。重点是路线最短。
  目前实测约 190 分，接近"已知全图"的理论上限约 194 分。
- **第二阶段**（`--stage 2`）：四队对抗，有公告和任务，需要 AI 网关和本场令牌。

规则允许两个阶段走不同分支，但必须在第一阶段开始前一起封存，所以放在同一份代码里。

## 四、代码文件地图

```text
contestant/
  rmtc_bot/
    __main__.py   命令行入口：run（比赛）/ replay（离线回放）/ analyze（看日志）/ doctor（环境检查）
    ros_node.py   和裁判通信：收感知、收公告、发动作、发队名
    protocol.py   感知解析与校验，动作格式
    engine.py     每 Tick 的主流程和动作打分（第二节第 5 步）
    planner.py    地图记忆、寻路、选目标（第二节第 2、4 步）
    ai.py         调用统一 AI 网关（后台线程）
    events.py     检查模型输出，回答"某格某时刻有没有事件"
    scoring.py    分数公式
    policies.py   四种决策类型
    audit.py      日志
    config.py     所有参数及其默认值
  config/
    default.json          封存参数（不要改）
    decision_config.json  现场唯一可改项：decision_type
  scripts/run_contestant.sh   正式比赛启动脚本
  tests/                       单元测试
```

**版本状态**：当前代码是 2026-10-29 冻结的版本（freeze-1029）。近战前瞻、对手建模、残局缓冲、开局改进等试验都没有通过比赛条件测试，相关代码已删除；参数以 `config/default.json` 为准，比赛时不要修改。

## 五、部署（在比赛设备上做一次）

### 1. 准备环境

比赛设备需要：

- **Ubuntu 22.04**（自带 Python 3.10，够用）；
- **ROS 2 Humble**。没装的话按 ROS 官方文档添加软件源后安装（需要管理员权限，自己在终端执行）：

  ```bash
  sudo apt install ros-humble-ros-base
  ```

程序只用 Python 标准库和 ROS 自带的 `rclpy`、`std_msgs`，**不需要 pip 安装任何东西**。

### 2. 放代码

把整个 `contestant` 文件夹拷到比赛设备，比如 `~/contestant`。拷贝时不要带 `logs/` 和 `work/` 里的旧日志。

### 3. 自检

```bash
cd ~/contestant
source /opt/ros/humble/setup.bash
python3 -m rmtc_bot doctor
```

应看到 `rclpy`、`std_msgs` 可用。再跑一遍测试：

```bash
python3 -m unittest discover -s tests -t . -q
```

最后一行显示 `OK` 即可。

## 六、启动参赛程序

比赛前主办方会通知：**席位**（A/B/C/D）、**ROS 域编号**、**AI 网关地址**、**本场令牌**、可能还有**模型名**。

### 第一阶段

```bash
cd ~/contestant
source /opt/ros/humble/setup.bash
export ROS_LOCALHOST_ONLY=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
bash scripts/run_contestant.sh --stage 1 --team A --domain-id 本场域编号 --name '秋天' \
  --config config/default.json --decision-config config/decision_config.json --log logs/stage1.jsonl
```

### 第二阶段

```bash
cd ~/contestant
source /opt/ros/humble/setup.bash
export ROS_LOCALHOST_ONLY=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export RMTC_AI_URL='http://通知的地址:端口/v1/chat/completions'
read -rsp '本场席位令牌: ' RMTC_TEAM_TOKEN; echo
export RMTC_TEAM_TOKEN
bash scripts/run_contestant.sh --stage 2 --team 本场席位 --domain-id 本场域编号 --name '秋天' \
  --config config/default.json --decision-config config/decision_config.json --log logs/match.jsonl
```

- `read -rsp` 那一行会提示输入令牌，**输入时屏幕不显示**，回车即可。令牌不要写进命令行、文件或截图。
- **不要设置模型**：比赛只允许统一默认模型，程序不发送 model 字段；若设置了 `RMTC_AI_MODEL`，正式启动会直接报错退出。
- 启动成功会看到 `Ready: /team_X; waiting for perception and referee start`，之后裁判开赛，程序自动开始。
- 结束程序：按 `Ctrl+C`。

### 比赛后检查

另开一个终端：

```bash
cd ~/contestant
python3 -m rmtc_bot analyze logs/match.jsonl
```

重点看：

| 字段 | 正常情况 |
|---|---|
| `session_id`、`team` | 和本场一致 |
| `decisions`、`receipts` | 都大于 0，而且数量接近（说明动作真的被裁判执行了） |
| `invalid_actions`、`receipt_errors`、`perception_rejections` | 0 或为空 |
| `http_successes`（第二阶段） | ≥ 1（说明 AI 网关调用成功过） |
| `planning_max_ms` | 远小于节拍（第二阶段 500 ms） |

### 现场允许改的唯一参数

确实需要换风格时，经裁判批准后修改 `config/decision_config.json`，例如：

```json
{"decision_type":"survive"}
```

然后按 `Ctrl+C` 停止、重新执行启动命令才会生效。其他文件都不要改。

## 七、常见问题

| 现象 | 原因和处理 |
|---|---|
| 一直停在 `waiting for perception and referee start` | 域编号不对、没设 `ROS_LOCALHOST_ONLY=0`、网线没接或不在指定网络。新开终端执行 `source /opt/ros/humble/setup.bash` 后运行 `ros2 topic list`（用同一个域编号：`export ROS_DOMAIN_ID=编号`），应能看到 `/team_X/perception` |
| 日志出现 `token_refresh_required` | 换场了。令牌只对一场有效，`Ctrl+C` 后用新令牌重新执行 `read -rsp` 和启动命令 |
| `http_successes` 为 0 | 网关地址写错（必须以 `/v1/chat/completions` 结尾）、令牌错误或额度用完。程序仍会照常决策，只是不理解公告 |
| 程序报错退出 | 向裁判登记后用同样的命令重启；同一场内重启会根据感知自动接上（每阶段原则上最多重启 2 次） |
| 启动时报 `stage 1 only permits seat A` | 第一阶段只能用 `--team A` |
